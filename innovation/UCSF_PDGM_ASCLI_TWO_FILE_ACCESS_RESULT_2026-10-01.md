# UCSF-PDGM official ascli two-file access result

This follows the [frozen two-file header protocol](UCSF_PDGM_TWO_FILE_HEADER_PROTOCOL_2026-10-01.md) and the [IBM ascli execution plan/amendment](IBM_ASCLI_UCSF_TWO_FILE_EXECUTION_PLAN_2026-10-01.md). The selected case and two exact NIfTI member paths were unchanged throughout. No GPU or locked IXI test was used. No patient pixel was decoded.

IBM's [official ascli manual](literature/source_cache/ibm_aspera_cli_manual_2026-10-01/index.json) documents Faspex 5 public-link authentication, per-file `packages receive`, the `@env:` reader and a Windows portable package. The IBM [release record](literature/source_cache/ibm_aspera_cli_release_gate_2026-10-01/index.json) lists version 4.27.3; its 41,246,637-byte ZIP was downloaded under `innovation/tools`, safely extracted, and its SHA-256 matched the official `64c58a092fa7609ffeb8a212cc8bbd70fb0147d4498d3c909909c8dca29b01fd`. `ascli -v` returned `4.27.3`; no Ruby installation or PATH change occurred. IBM's Connect SDK README says the older Connect SDK is deprecated; the current JS SDK still requires a supported transfer client. These SDKs were not used to transfer files.

The [sanitized read-only browse attempts](literature/source_cache/ibm_ascli_ucsf_browse_v5_2026-10-01.json) identify a local environment issue: inherited proxy variables pointed ascli at `127.0.0.1:9`. Clearing those variables **only for the child process** allowed the official CLI to authenticate to the public Faspex link and browse package root successfully (exit 0, `UCSF-PDGM-v5` present). The first failed Python probes used `TemporaryDirectory` ACLs that blocked cleanup; both exact empty probe directories were inspected and removed. Subsequent CLI homes were isolated under `innovation/data` and removed after use.

Before a file transfer, a [read-only official Connect transfer-spec request](literature/source_cache/ucsf_two_file_transfer_spec_probe_2026-10-01.json) returned HTTP 201 for **exactly the two frozen paths**, `source_root=null`, `zip_required=null`, direction `receive`, token authentication. A [second read-only request](literature/source_cache/ucsf_ascli_recipient_query_probe_2026-10-01.json) included the `recipient_user_id` query parameter added by IBM's Faspex5 plugin and still returned HTTP 201 with the same two paths. No raw token, cookie or complete specification was saved.

The first bounded [ascli receive attempt](literature/source_cache/ucsf_two_file_ascli_pilot_2026-10-01.json) passed the two paths as positional file arguments. The second used IBM's documented `--sources=@lines:@file:` with the [exact two-line source list](literature/source_cache/ucsf_ascli_exact_sources_2026-10-01.txt); `ascli config echo` had reproduced exactly those two paths before transfer. Both attempts used an empty destination, isolated home, 5,000 kbps target, low rate policy, zero retries, 10 MB local byte cap and 120-second deadline. Each returned Faspex HTTP 500 with `NoMethodError - undefined method 'starts_with?' for nil` and **zero files, zero bytes**. Server traces were `9fa2d2a1-43f7-4698-8003-9b7b640aee24` and `d3d403b6-bd17-4b49-916c-2cf4bbac91ec`. All CLI-created homes were removed; no `ruby`, `ascli` or `ascp` process remains from these attempts.

The available evidence does **not** identify the exact server-side root cause or prove that the symbolic links are invalid. The manual API specification succeeds, whereas this ascli/plugin path triggers 500. Under the prewritten stop rule, no more CLI parameter variants or package-wide transfer were attempted. The two NIfTI headers, T2/mask affine and independent-patient gate remain unverified. A later supported Connect desktop-client route or TCIA support response could change access, but no external message was sent. The exact two-file protocol remains the only permissible header pilot for this case.
