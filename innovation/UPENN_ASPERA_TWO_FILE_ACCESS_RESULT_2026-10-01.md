# UPENN official Aspera two-file access pilot

This follows the [frozen file-level inventory and pilot rule](UPENN_NIFTI_OFFICIAL_INVENTORY_AND_PILOT_PLAN_2026-10-01.md). The public Faspex package 604 browser listed the preselected `UPENN-GBM-00002_11` T2 NIfTI (declared 1,775,300 bytes) and corrected segmentation (51,227 bytes). No other source path was requested. All source strings were compared exactly with the previously archived package root and the two frozen paths before launching a transfer. A 10 MB local byte cap, 120-second deadline and 5 Mbps rate limit were set. The GPU, running training, locked IXI test and patient pixels were untouched.

IBM's public [Connect download page index](literature/source_cache/ibm_aspera_downloads_2026-10-01/index.json) led to a 53,911,552-byte vendor MSI, SHA-256 `4ec4436b019f336c05557a4df9f77488913c5338e0c69c77c7d1cf859746fc57`. Authenticode verification found a valid IBM signature. The embedded CAB was read with Windows Installer APIs without running an installation transaction. Its SHA-256 is `f86eb547cdb2dde58eba73519310b8e27cfafeba7793523ef4596960b37af161`; the portable `ascp.exe`, support DLL, packaged token-auth key and `aspera-license` were extracted under [tools](tools/ibm_aspera_connect_4.2.19.956/). The license's SHA-256 is `e9be46f5b17413b6225d875edce8eb28870df2f387d788344aac3aa1d86b228a`. No system installation or environment change occurred.

The official public-link session issued a `connect` transfer specification for exactly two paths. Unlike the earlier `http_gateway` specification, it had `source_root=null`, two full `source` paths and `zip_required=null`; both full paths matched the frozen root plus requested file paths. This describes **different transfer-spec formats**, not proof that `zip_required=true` on the HTTP-gateway route would download an entire package. The `connect` route gave token authentication and TCP/UDP port 33001. Token and cookie were passed only as child-process environment variables, never as command arguments or saved in a spec/report. The script's [nonsecret attempt records](literature/source_cache/upenn_gbm_two_file_ascp_pilot_v9_2026-10-01.json) and [source](literature/try_upenn_two_file_ascp.py) retain exact scope checks and failure stages.

The first attempts stopped before data transfer: the `connect` path format differed from the earlier HTTP format; Windows `ascp` rejected `--symbolic-links`; then the portable distribution lacked its packaged license until extracted. With all these corrected, the final bounded attempt returned `ascp.exe: failed to authenticate, exiting.` (exit 1). **Zero files and zero bytes** were received. Generated `ascp` diagnostic logs were removed; no temporary credential, full transfer specification or raw diagnostic log was archived. The reason for the authentication failure is unresolved: possible CLI token/cookie interpretation, key usage or server-side behavior have not been distinguished. It is not evidence that the public symbolic links are invalid.

Under the prewritten stop rule, no further CLI guessing, whole-package transfer or pixel inspection follows from this result. NIfTI header shape/affine, mask contents and same-grid eligibility remain unverified. A later attempt should use a documented IBM Connect client or vendor-supported transfer-spec invocation, still limited to the exact two files, and only then perform the planned header-only check. Atlas NIfTI labels must never be overlaid on the separate frozen processed-DICOM cohort without a validated transform.
